# Сервис распознавания медицинских анализов (MedLab OCR)

Бэкенд на FastAPI для автоматического парсинга и структурирования медицинских бланков. Система принимает файлы разных форматов, вытаскивает из них сырой текст и готовит данные для дальнейшего анализа.

## Что уже сделано в проекте

*   **REST API на FastAPI:** Написана архитектура с разделением на роутеры, сервисы и схемы валидации.
*   **Валидация данных:** Внедрен Pydantic v2 (DTO) для жесткого контроля входящих и исходящих данных, настройки пагинации и фильтрации списков.
*   **Асинхронная база данных:** Подключена PostgreSQL через SQLAlchemy + asyncpg, настроена ленивая инициализация сессий через Depends.
*   **Мультиформатный OCR-слой:** Написаны парсеры под разные типы файлов:
    *   Изображения (PNG, JPEG, WEBP) через Tesseract OCR.
    *   Документы PDF через конвертацию страниц в байты и поочередный парсинг.
    *   Таблицы (CSV, Excel) через Pandas с автоматическим считыванием структуры.
*   **Оптимизация потоков:** Все тяжелые синхронные операции парсинга (библиотеки pytesseract, pandas, pdf2image) изолированы и запускаются в отдельном пуле потоков через run_in_threadpool, чтобы не блокировать основной асинхронный цикл (event loop) сервера.

---

## Важный технический кейс (Post-Mortem ошибки с пулом потоков)

В процессе настройки логирования времени работы парсеров столкнулся с неочевидной проблемой, которая отлично показывает внутреннее устройство Python и FastAPI.

### Описание проблемы ~никому не пожелаю разбираться в этом~
Когда функции парсинга были обернуты в кастомный синхронный декоратор времени (который использовал классический functools.wraps и сигнатуру *args, **kwargs), вызов через пул потоков run_in_threadpool начал падать в базу данных с ошибкой:
`TypeError: the first argument must be callable`

При этом код самого декоратора и логика вызова были синтаксически правильными, а без декоратора всё работало.

### Причина сбоя
Под капотом FastAPI использует библиотеку AnyIO, которая перед отправкой функции в ThreadPoolExecutor жестко инспектирует её аргументы через встроенный модуль `inspect`. 

Несмотря на то, что functools.wraps копирует имя функции и её docstring, он скрывает реальную сигнатуру параметров (например, file_bytes: bytes, is_csv: bool) за общей оберткой `*args, **kwargs`. Механизм инспекции AnyIO запутался в порядке передачи позиционных и именованных аргументов, из-за чего попытался выполнить операцию вызова над некорректным внутренним объектом.

### Как это было решено
1. **Чистые функции:** Избавился от декораторов со свободной сигнатурой (`*args, **kwargs`) на функциях, которые передаются внутрь системных механизмов фреймворка. Парсеры теперь остаются «голыми» функциями модуля.
2. **Явный замер:** Логирование и замер времени выполнения синхронных тяжелых задач перенесены напрямую внутрь асинхронного метода-фасада `extract_text` прямо перед отправкой задачи в пул потоков.

Этот кейс помог на практике разобраться, как фреймворки работают с метаданными функций через inspect и почему универсальные декораторы могут ломать сторонние библиотеки.
